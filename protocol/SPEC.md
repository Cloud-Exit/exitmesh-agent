# ExitMesh History Protocol v1

| | |
|---|---|
|Status|Draft 0.1|
|Protocol version|1|
|State schema version|1|
|Scope|Record schema, encoding, hashing, chain, fold, reconstruction, sessions, ownership, tunnel binding|

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as described in RFC 2119.

This document is normative for every writer (Kubernetes coordinator, Linux host agent) and every reader (the ExitMesh control plane, export tooling). The Go implementation lives in `pkg/protocol`; the language-neutral reference oracle lives in `protocol/reference`. Both MUST agree on every vector in `protocol/vectors`.

## 1. Terms

|Term|Meaning|
|---|---|
|Target|A Kubernetes cluster or a Linux host, identified by `target_id`.|
|Writer|The single process allowed to append records for a target: the coordinator for a cluster, the host agent for a host.|
|Spool|The writer's durable local record store. A writer ID is created with the spool and never changes for its lifetime.|
|Epoch|A contiguous chain of records produced by one writer. Sequences never overlap across epochs.|
|Record|An immutable, typed, deterministically encoded unit of history: checkpoint, delta, range, or finding event.|
|Chain|The ordered records of one epoch, linked by `parent` and by the chain hash.|
|Committed head|The highest sequence of an epoch that the control plane has durably committed.|
|Anchor|A checkpoint inside the chain that can serve as a reconstruction base.|
|Watermark (W)|The sequence at which a writer captures the finding lifecycle summary and the pending anchor during a resume (section 8.4).|

## 2. Identity

|Field|Type|Rules|
|---|---|---|
|`target_id`|text, 1 to 128 bytes of `[A-Za-z0-9._-]`|Assigned by the control plane at enrollment. Never derived from cluster names, hostnames, or machine IDs.|
|`writer_id`|16 bytes|Generated from a CSPRNG when the spool is created. Persisted in the spool.|
|`incarnation`|unsigned integer, at least 1|Incremented and made durable on every writer start, under the spool lock, before any connection is attempted.|
|`epoch`|16 bytes|A UUIDv7 generated by the writer when it opens the epoch. The writer can open an epoch while offline; the control plane orders epochs by registration.|
|`seq`|unsigned integer, at least 1|Assigned by the writer, strictly increasing within an epoch.|

A record ID is the triple (`target_id`, `epoch`, `seq`). A record ID, once transmitted, is never bound to different content (section 8.6).

## 3. Encoding

### 3.1 Deterministic CBOR

Every record is a single CBOR data item (RFC 8949) encoded with core deterministic encoding (RFC 8949 section 4.2.1):

- Integers, lengths, and tags use the shortest form.
- Indefinite-length items are not used.
- Map keys are sorted by the bytewise lexicographic order of their deterministic encodings.
- Floating-point values use the shortest of half, single, or double precision that preserves the value exactly. NaN and infinities MUST NOT appear.
- No CBOR tags are used. Simple values other than `false`, `true`, and `null` MUST NOT appear. `null` appears only where this document allows it.

### 3.2 Strict decoding

A decoder MUST reject:

- Trailing bytes after the record item.
- Duplicate map keys.
- Indefinite-length items, non-shortest integers or lengths, or tags.
- Invalid UTF-8 in text strings.
- Nesting deeper than 32 levels, arrays or maps with more than 1,048,576 elements, or a record larger than 4 MiB.
- Any record whose re-encoding under section 3.1 does not equal the input bytes (the re-encode check).

Records are stored, transmitted, and hashed as their exact bytes. A reader never re-serializes a record to store or forward it.

### 3.3 Values

A field value in resource state, edge attributes, finding facts, and similar places is one of: text string, byte string, integer in the range [-2^63, 2^64-1], `true`, `false`, finite float, array of values, or map from text string to value. `null` is not a value; it appears only in update changes (section 4.3) where it means "field removed".

### 3.4 Extension keys

Envelope and body maps use unsigned integer keys. Keys 1000 and above are extension keys: a reader MUST preserve them (they are covered by the record hash because the record is kept as bytes) and MUST ignore extension keys it does not understand. An unknown key below 1000 makes the record unsupported, and the reader MUST reject it with reason `unsupported_field`. Op maps (4.3), including a scope status nested in an op, carry no extension keys; an op containing one is rejected with `unsupported_field`, because the fold re-encodes ops. Extension keys in a checkpoint's scope statuses are not part of state and do not enter the state hash. Extension values may be any data item allowed by 3.1, including `null`. A fold (section 5) re-encodes the records it replaces and drops their extension keys; writers therefore place extension keys only in information that may be lost on coalescing.

### 3.5 Canonical optional keys and error codes

An optional key (marked `?` in CDDL) is omitted when its value would be zero, `false`, empty text, an empty array, or an empty map; a record carrying such a key with such a value is rejected with `malformed`, so every record has exactly one accepted encoding. Record identity fields, `uid`, `kind`, edge `from`, `type`, and `to`, scope keys, finding ids, and deduplication keys are non-empty.

Structural errors (wrong type, missing required key) are `malformed` outside ops and `invalid_op` inside ops, including a delta with an empty op list. A protocol major version other than 1 is `unsupported_field`.

## 4. Records

### 4.1 Envelope

```cddl
record = {
  0: 1,                 ; protocol major version
  1: record-type,
  2: target-id,
  3: epoch,
  4: seq,
  5: writer-id,
  6: incarnation,
  7: parent,            ; sequence of the chain predecessor, 0 for the first record of an epoch
  8: base,              ; sequence of the governing checkpoint
  9: time,              ; emit time, milliseconds since the Unix epoch
  10: schema,           ; state schema version
  11: body,
  * ext-key => any
}
record-type = 1 / 2 / 3 / 4   ; checkpoint, delta, range, finding
target-id = tstr
epoch = bstr .size 16
writer-id = bstr .size 16
seq = uint
incarnation = uint
parent = uint
base = uint
time = uint
schema = uint
ext-key = uint .ge 1000
```

Chain structure rules. A reader MUST reject a record that violates any of them with reason `invalid_chain`:

1. The first record of an epoch is a checkpoint with `seq` 1, `parent` 0, `base` 1.
2. For a checkpoint, delta, or finding record, `seq = parent + 1`.
3. For a range record with span [a, b], `seq = b`, `parent = a - 1`, and `1 < a <= b`.
4. For a checkpoint, `base = seq`. For any other record, `base` is the sequence of the most recent checkpoint whose sequence is at most `parent`.
5. `writer_id` equals the epoch's owning writer, and `incarnation` is at least 1.

### 4.2 Checkpoint body

```cddl
checkpoint-body = {
  0: checkpoint-reason,
  1: interval,
  2: [* resource],        ; sorted by uid
  3: [* edge],            ; sorted by edge key
  4: { * scope-key => scope-status },
  5: [* tstr],            ; capabilities, sorted, unique
  6: state-hash,
  ? 7: epoch,             ; previous epoch closed by this one (first checkpoint of an epoch only)
  ? 8: uint,              ; committed head of the previous epoch as known to the writer (first checkpoint only; present only with key 7)
}
checkpoint-reason = 1 / 2 / 3 / 4 / 5
  ; 1 initial enrollment, 2 periodic anchor, 3 rebaseline, 4 writer change, 5 replay anchor
interval = [start: uint, end: uint]   ; observation interval in ms, start <= end
resource = [uid: tstr, kind: tstr, ns: tstr, name: tstr, fields: { * tstr => value }]
edge = [from: tstr, type: tstr, to: tstr, attrs: { * tstr => value }]
scope-key = tstr
scope-status = {
  0: scope-state,         ; 0 complete, 1 partial, 2 unavailable
  ? 1: tstr,              ; reason code
  ? 2: uint,              ; since, ms
}
state-hash = bstr .size 32
```

`kind` is `<group>/<Kind>` for grouped Kubernetes kinds (for example `apps/Deployment`), the bare Kind for the core group (for example `Pod`), and `host/<Kind>` for host facts. `ns` is the empty string for cluster-scoped resources. The edge key is the triple (`from`, `type`, `to`), compared bytewise element by element.

Scope keys are opaque to this protocol and defined by the state schema. Permission loss, collection failure, and scope removal are expressed through scope status and delete reasons, never as plain deletion (section 4.3).

A checkpoint does not change state. A checkpoint other than the first of an epoch asserts that the state at `parent` equals its content (section 6.3).

### 4.3 Delta body

```cddl
delta-body = {
  0: [+ op],
  ? 1: uint,              ; flags: bit 0 synthetic (relist and diff), bit 1 metric facts
  ? 2: interval,          ; uncertainty interval (relist window)
}
op = create / update / delete / edge-add / edge-remove / edge-replace / scope-set
create       = { 0: 1, 1: uid, 2: kind, 3: ns, 4: name, 5: fields }
update       = { 0: 2, 1: uid, 5: changes }
delete       = { 0: 3, 1: uid, 6: delete-reason }
edge-add     = { 0: 4, 1: from, 7: type, 8: to, 9: attrs }
edge-remove  = { 0: 5, 1: from, 7: type, 8: to, 9: attrs }      ; the removed attributes
edge-replace = { 0: 6, 1: from, 7: type, 8: to, 9: attrs, 10: prev-attrs }
scope-set    = { 0: 7, 11: scope-key, 12: scope-status }
uid = tstr
fields = { * tstr => value }
changes = { + tstr => value / null }                            ; null removes the field
delete-reason = 1 / 2                                            ; 1 deleted, 2 scope removed
```

Application rules. A reader MUST reject a delta that violates any of them with reason `invalid_op`:

- `create` requires that `uid` is absent. `uid` is never reused: a recreated object with the same name is a new UID.
- `update` and `delete` require that `uid` is present. `update` never changes `kind`, `ns`, or `name`.
- Applying `changes` sets each non-null value and removes each key whose value is `null`. Removing an absent key is a no-op.
- `edge-add` requires the edge key to be absent; `edge-remove` and `edge-replace` require it to be present.
- `scope-set` replaces the status of the scope key.
- A single delta MUST NOT contain two ops for the same UID, edge key, or scope key.

Writers suppress deltas whose normalized representation is unchanged. Metric facts are resource fields under the `metric.` prefix and are updated with ordinary `update` ops carrying flag bit 1.

### 4.4 Range body

```cddl
range-body = {
  0: [* op],                        ; folded ops in canonical order (section 5.3)
  1: [a: uint, b: uint],            ; covered span
  2: [* [seq: uint, finding-body]], ; preserved finding events, ascending seq
  ? 3: uint,                        ; OR of covered delta flags
  ? 4: [* interval],                ; covered uncertainty intervals, in order
}
```

A range record replaces sequences a through b. Sequences a through b-1 are unavailable for exact reconstruction; the span is the unavailable marker. The state after the range record is exact.

### 4.5 Finding body

```cddl
finding-body = {
  0: tstr,                  ; finding id (section 7)
  1: tstr,                  ; deduplication key
  2: transition,
  3: provenance,
  4: tstr,                  ; category
  5: severity,
  6: uint,                  ; evaluation time, ms
  7: uint,                  ; first seen, ms
  8: uint,                  ; last seen, ms
  9: uint,                  ; occurrence count
  10: [* tstr],             ; affected resource uids, sorted, unique
  ? 11: { * tstr => value },; matched condition and relevant normalized facts
  ? 12: [* evidence],
  ? 13: uint,               ; flags (below)
  ? 14: tstr,               ; source node
  ? 15: { * tstr => tstr }, ; labels
  ? 16: tstr,               ; summary
  ? 17: [* suggestion],
  ? 18: [* tstr],           ; coverage limitations
}
transition = 1 / 2 / 3 / 4 / 5    ; firing, update, resolved, stale, fresh
severity = 1 / 2 / 3 / 4 / 5      ; info, low, medium, high, critical
provenance = rule-provenance / query-provenance
rule-provenance = { 0: 1, 1: tstr, 2: uint, 3: tstr }    ; rule id, rule version, bundle version
query-provenance = { 0: 2, 4: bstr .size 32, 5: tstr }  ; query hash, requester
evidence = {
  0: tstr,                  ; source (for example "logs:<stream>" or "promql")
  1: uint,                  ; time, ms
  2: tstr,                  ; redacted sample
  ? 3: uint,                ; repeat count
  ? 4: { * tstr => tstr },  ; labels
  ? 5: bool,                ; truncated
  ? 6: bool,                ; non-matching context line
}
suggestion = { 0: tstr, 1: tstr, ? 2: tstr }   ; language, query, source
```

Finding flags: bit 0 evidence truncated, bit 1 evidence limited, bit 2 incomplete coverage, bit 3 samples compacted to counts, bit 4 late on the writer side (evaluation older than the writer's late threshold at emit).

Transitions: `firing` opens an episode; `update` carries new counts or samples for an open episode; `resolved` closes it on an explicit recovery condition; `stale` marks evaluation stale (loss of telemetry, coverage, or connectivity) and never resolves; `fresh` reports that evaluation resumed with the episode still firing.

## 5. Fold

The fold turns a contiguous run of never-transmitted delta, range, and finding records with sequences a through b into one range record at b. It uses the records alone: no base state and no reverse application.

### 5.1 Resources

For each UID, take the first and the last op touching it in the run.

- Existed before a: the first op is `update` or `delete`. Absent before a: the first op is `create`.
- Exists at b: the last op is `create` or `update`. Absent at b: the last op is `delete`.

|Before|At b|Folded op|
|---|---|---|
|absent|absent|none (create then delete cancels)|
|absent|present|`create` with the create fields, then every later `changes` applied in order|
|present|absent|`delete` with the reason of the last delete|
|present|present|`update` whose changes are the in-order merge of every `changes` map, last writer wins, `null` preserved|

### 5.2 Edges and scopes

For each edge key, take the first and the last op.

- Existed before a with attributes P: the first op is `edge-remove` (P = its attrs) or `edge-replace` (P = its prev-attrs). Absent before a: the first op is `edge-add`.
- Exists at b with attributes Q: the last op is `edge-add` or `edge-replace` (Q = its attrs). Absent at b: the last op is `edge-remove`.

|Before|At b|Folded op|
|---|---|---|
|absent|absent|none|
|absent|present Q|`edge-add` Q|
|present P|absent|`edge-remove` P|
|present P|present Q, P = Q|none|
|present P|present Q, P != Q|`edge-replace` attrs Q, prev-attrs P|

Attribute equality is equality of deterministic encodings. For each scope key, the folded op is the last `scope-set`.

### 5.3 Canonical order and range fields

Folded ops are ordered: resource ops by UID, then edge ops by edge key, then scope ops by scope key, each bytewise. Finding events from the run are copied in ascending sequence with their original sequences. Flags are the OR of covered delta and range flags. Uncertainty intervals are concatenated in sequence order. When a range record is part of the run, its ops and preserved finding events are expanded in place; when it is the first record of the run, its span start becomes the new `a`. Because coalescing always takes the oldest never-transmitted run, a range record is in practice only ever the first record of a later run.

Because deltas carry full values of changed fields and UIDs are never reused, applying the folded ops to the state at a-1 yields exactly the state at b.

## 6. State and reconstruction

### 6.1 State

State is a triple: resources (UID to kind, namespace, name, fields), edges (edge key to attributes), and scopes (scope key to status).

### 6.2 State hash

```
state-canon = [
  [* resource],                     ; sorted by uid
  [* edge],                         ; sorted by edge key
  { * scope-key => scope-status },
]
state_hash = SHA-256("EMHPv1/state" || 0x00 || cbor(state-canon))
```

The empty state is `[[], [], {}]`.

### 6.3 Reconstruction

State at sequence n of an epoch is computed by taking the governing checkpoint and applying every later delta and range record up to n in chain order. Finding records do not change state.

- Sequences strictly inside a range span (a through b-1) return `unavailable`.
- A checkpoint other than the first of an epoch is verified: the state hash of the state at its `parent` MUST equal its `state-hash`. A mismatch is a reconstruction boundary: reconstruction below the checkpoint remains as computed, reconstruction from the checkpoint on uses its content, and the boundary is reported.
- A checkpoint's own content MUST hash to its `state-hash`; otherwise the record is rejected with `invalid_state_hash`.

## 7. Hashes and identifiers

All hashes are SHA-256 with a domain separation prefix followed by one zero byte.

```
record_hash      = SHA-256("EMHPv1/record" || 0x00 || record-bytes)
genesis          = SHA-256("EMHPv1/genesis" || 0x00 || cbor([target_id, epoch, writer_id]))
chain_hash(r)    = SHA-256("EMHPv1/chain" || 0x00 || chain_hash(parent(r)) || record_hash(r))
                   where chain_hash(parent 0) = genesis
finding_id       = hex(SHA-256("EMHPv1/finding" || 0x00 || cbor([target_id, dedup_key, first_seen]))[0:16])
query_hash       = SHA-256("EMHPv1/query" || 0x00 || cbor([language, normalized_query, source]))
```

The chain hash of a sequence is the chain hash of the record at that sequence. After a range record at b replaces a through b, the records after b keep their bytes; only their chain hashes change, and only the writer, which has never transmitted them, recomputes them.

## 8. Sessions, ownership, and delivery

### 8.1 Writer state

A writer persists in its spool, durably and atomically with record state changes:

- `writer_id`, `incarnation`, current `epoch`, next sequence;
- per record: state (never-transmitted, transmitted-unconfirmed, committed), record hash, chain hash;
- `last_committed`: the committed head sequence and chain hash last confirmed by the control plane;
- the credential and `target_id`.

A record moves from never-transmitted to transmitted-unconfirmed durably before the first byte of it is sent. Transmitted records are immutable and are resent byte-identical. A record is deleted only after the control plane reports it committed. The bytes of transmitted-unconfirmed records in flight are bounded by the session window (default 8 MiB); transmission pauses when the window is full.

### 8.2 Control plane state

Per target, serialized so two resumes cannot both succeed:

- owning writer of the open epoch, and the set of retired writers;
- highest incarnation seen per writer;
- epochs: owner, status (open or closed), committed head sequence and chain hash, closing sequence;
- active session, if any, with its writer and incarnation;
- for hosts: enrolled machine ID, conflict flag, pending administrator binding.

The control plane commits a record durably before acknowledging it. It accepts a record ID once; the same ID with the same record hash is an idempotent duplicate; the same ID with a different hash is a divergence.

### 8.3 Ownership decision table

On `history.hello` the control plane evaluates, in order, and the first matching row decides. `W` is the presented writer, `I` its incarnation, `E` its epoch, `L`/`P` its last committed sequence and chain hash.

|#|Condition|Decision|Writer action|
|---|---|---|---|
|1|Credential invalid, revoked, or target de-enrolled|reject `unauthorized`|Stop, report.|
|2|Target has an unresolved identity conflict|reject `identity_conflict`|Keep spooling, report.|
|3|Host target and presented machine ID differs from the enrolled one|set conflict, reject `identity_conflict`|Keep spooling, report.|
|4|`W` is a retired writer|audit, reject `writer_retired`|Stop writing, report.|
|5|`E` is known and closed|audit, reject `epoch_closed`|Stop writing, report. Never open a new epoch in response.|
|6|`E` is known, open, and owned by a writer other than `W`|audit, reject `not_owner`|Stop writing, report.|
|7|`I` is lower than the highest incarnation seen for `W`|audit, reject `stale_incarnation`|Stop writing.|
|8|An active session exists with the same `W` and `I`|reject the new session `identity_conflict`, alarm|Keep spooling, retry with backoff.|
|9|`E` is known and open, owned by `W`, and `L`/`P` does not match the committed chain (L above the committed head, or chain hash at L differs)|reject `divergence`|Rebaseline (8.6).|
|10|`E` is known, open, owned by `W`|resume; supersede any active session of `W` with lower `I`|Resume and drain (8.4).|
|11|`E` is unknown and the target has no epochs|register `W` as owner, open `E`|Resume and drain from head 0.|
|12|`E` is unknown, `W` owns the open epoch, and `E` declares that epoch as its previous epoch (rebaseline)|close the previous epoch at its committed head, open `E`|Resume and drain.|
|13|`E` is unknown, `W` differs from the owner, cluster target|retire the previous owner, close its epoch at its committed head, register `W`, open `E`|Resume and drain.|
|14|`E` is unknown, `W` differs from the owner, host target, and an administrator binding is pending|as row 13, clear the binding|Resume and drain.|
|15|`E` is unknown, `W` differs from the owner, host target|set conflict, reject `identity_conflict`|Keep spooling, report.|
|16|Otherwise|reject `invalid_hello`|Report.|

The highest incarnation seen for `W` is raised to `I` on rows 10 to 14. On rows 10 and 12 an active session of `W` with a lower incarnation is superseded; on rows 13 and 14 the active session of the retired owner, if any, is superseded. A superseded session receives `session.superseded`, and any frame it sends afterwards is rejected. Rows 3, 8, and 15 raise an alarm to the administrator; rows 12 to 14 are audited as ownership changes. Records for a closed epoch are audited and never applied. Every rejection is audited with the presented identity.

### 8.4 Resume and drain

After a successful hello the writer runs, in order:

1. The hello result carries the committed head H of `E` with its chain hash.
2. If the writer transmitted a record at H, it compares the chain hash; a mismatch is a divergence (8.6). If H is above the highest sequence the writer ever assigned, it is a divergence. Otherwise the writer deletes every spooled record with sequence at most H and records H as `last_committed`. This resolves commits whose acknowledgement was lost.
3. If records remain above H, the writer captures, atomically at one new sequence W, the finding lifecycle summary as of W and the current state as a replay-anchor checkpoint (reason 5) at W. W is the replay watermark. No finding transition and no state change can be assigned a sequence between the two captures, because both are taken under the writer's sequence lock.
4. The writer sends `history.summary`, then the replay anchor record.
5. It replays spooled records above H in order under a rate limit, then continues with live records.
6. When the committed head reaches W-1, the control plane verifies the replay anchor's state hash against the replayed state before treating it as a regular anchor. A mismatch opens a reconstruction boundary and is reported.

If no records remain above H, steps 3 to 6 are skipped. A writer that is unreachable does not emit periodic anchors; it keeps one local recovery snapshot, replaced in place, and relies on the replay anchor at reconnect.

### 8.5 Notification semantics

The control plane makes notification decisions for the backlog from the summary only: a finding resolved in the summary sends no notification; a finding still firing notifies once, labeled late with its original evaluation time. Replayed finding records at or below W update history and never notify. Finding records above W follow normal notification.

### 8.6 Divergence and rebaseline

A divergence is detected when the control plane rejects a record ID with a different hash, when hello row 9 matches, or when resume step 2 finds a mismatch. The writer then:

1. deletes every spooled record above the committed head H;
2. opens a new epoch with reason rebaseline (checkpoint reason 3) that names the current epoch as its previous epoch and H as its previous head;
3. emits a full checkpoint as sequence 1 of the new epoch.

Record IDs transmitted above H are void with the closed epoch and are never reissued.

### 8.7 Coalescing

Only never-transmitted records are coalesced, oldest contiguous run first, never across a checkpoint. The replay anchor, once transmitted, is immutable. Rebaseline under pressure happens only when the fully coalesced never-transmitted suffix still exceeds capacity, and is reported as a reconstruction boundary.

## 9. Tunnel binding

### 9.1 Transport

- Enrollment: `POST https://<endpoint>/agent/v1/enroll`.
- Tunnel: WebSocket (RFC 6455) over TLS to `wss://<endpoint>/agent/v1/tunnel`, subprotocol `exitmesh.v1`, header `Authorization: Bearer <credential>`. The writer always dials out; nothing listens inbound.
- Text frames carry JSON-RPC 2.0 messages in both directions. Binary frames carry record batches.
- Keepalive: WebSocket ping every 20 seconds; a session with no traffic for 60 seconds is dead.
- Reconnect uses exponential backoff with full jitter, 1 second to 5 minutes. Disconnects never revoke credentials.

### 9.2 Enrollment

Request:

```json
{"token":"emx1_c_<target_id>_<secret>","writer_id":"<hex>","target_type":"kubernetes","machine_id":"<hex, hosts only>","hostname":"<hosts only>","agent":{"version":"0.1.0","protocol":1,"schema":1,"engine":1}}
```

Response:

```json
{"target_id":"t-123","credential":"<opaque>","credential_id":"c-1"}
```

Enrollment tokens have the form `emx1_<kind>_<id>_<secret>` with kind `c` (cluster target), `h` (host target), or `g` (host group). For `c` and `h` the id is the `target_id`, so an air-gapped writer knows its `target_id` without contacting the control plane. For `g` the id is the group id, and the writer learns its `target_id` from the response. A credential is bound server-side to the writer ID and, for hosts, the machine ID.

### 9.3 Record frames

```
binary-frame = frame-type (1 byte) || compression (1 byte) || payload
frame-type   = 0x01 record batch
compression  = 0x00 none / 0x01 zstd
payload      = cbor([+ bstr])        ; each element is one record's exact bytes; the payload itself is not hashed and need not be deterministic
```

Records in a batch belong to the session's epoch and are in chain order, except that the replay anchor is sent first during resume (8.4 step 4). A payload after decompression is at most 16 MiB.

### 9.4 JSON-RPC methods

Hashes and 16-byte identifiers are lowercase hex in JSON.

|`history.ack`|notification|`epoch`, `seq` (committed through), `chain_hash`|
|`history.reject`|notification|`epoch`, `seq`, `code` (`divergence`, `invalid_chain`, `invalid_op`, `unsupported_field`, `invalid_state_hash`, `epoch_closed`), `message`|
|`session.superseded`|notification|`session_id`|
|`bundle.available`|notification|`version`, `target_type`|
|`credential.rotate`|request|`credential`, `credential_id`; the writer persists it durably, then responds `{}`|
|`target.deenrolled`|notification|none; the writer stops and deletes its credential|
|`initialize`, `ping`, `tools/list`, `tools/call`|MCP requests|Investigation tools (9.5), served by the writer as an MCP server over the reverse channel|

Errors use JSON-RPC error objects with `data.code` set to one of the decision codes in 8.3.

### 9.5 Investigation tools

The writer advertises MCP tools `state.query`, `graph.query`, `promql.query`, `logql.query`, `logsql.query`, and `lookback.query`. Every call carries `scope` (namespaces, resources, nodes), `window` (`start`, `end` in ms), `limits`, `requester`, and `purpose`. Results carry `source`, `window`, `limits`, `truncated`, `limitations`, and the query hash. Results are never retained by the writer.

## 10. Export format

An air-gap export file is:

```
"EMHPX1" 0x0a || cbor-sequence(header, * record-bytes)
header = { "target_id": tstr, "writer_id": bstr, "incarnation": uint, "epoch": bstr,
           "last_committed": uint, "exported_at": uint, "agent_version": tstr }
```

Each record item is a byte string holding exact record bytes, in chain order. Importing a file into the control plane follows the same ownership table as a hello.

## 11. Compatibility

- A change to encoding, hashing, or envelope semantics is a protocol major version.
- New optional body keys use extension keys or a minor revision that readers of the same major version can ignore.
- The state schema version (envelope key 10) versions field catalogs; a reader that does not know a schema version still stores and chains the records.
